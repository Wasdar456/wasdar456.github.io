# Tokenizer

Tokenizer 是一个实现了 `encode` 和 `decode` 方法的类。

# Observations

## 1. Token 的基本观察

* 很多 token 是“空格 + 单词”的形式。
* Tokenizer 有一个重要指标：压缩比。
* 压缩比通常定义为：

$$
\text{Compression Ratio}
=
\frac{\text{Number of Bytes}}
{\text{Number of Tokens}}
$$

也就是：

$$
\text{byte/token}
$$

这里有一个常见说法：**增大词表可以提高压缩比。**

---

## 2. 增大词表与压缩比

例如，要压缩下面的字符串：

```text
人工智能人工智能人工智能
```

### 2.1 小词表

假设词表中只有单个汉字：

```text
人、工、智、能
```

编码后需要：

```text
人 工 智 能 人 工 智 能 人 工 智 能
```

一共需要 12 个 token。

### 2.2 大词表

假设词表中增加了一个词元：

```text
人工智能
```

编码后变成：

```text
人工智能 | 人工智能 | 人工智能
```

这样只需要 3 个 token。

虽然大词表中每个 token 的编号可能需要占用更多比特，但是 token 数量从 12 个下降到了 3 个，因此总体存储空间通常会减少。

假设词表大小为 $V$，那么区分一个 token 至少需要：

$$
\log_2 V
$$

比特。

如果文本被编码成 $N$ 个 token，那么在最简单的情况下，编码长度大约为：

$$
L \approx N\log_2 V
$$

增大词表时：

* $V$ 增大，单个 token 的编号变长；
* $N$ 减小，文本所需的 token 数量下降。

因此，增大词表能否提高压缩效果，取决于是否满足：

$$
N_{\text{new}}\log_2 V_{\text{new}}
<
N_{\text{old}}\log_2 V_{\text{old}}
$$

也就是说，只有当 token 数量下降带来的收益，大于单个 token 编号变长带来的额外开销时，总编码长度才会减少。

---

## 3. 大词表带来的数据稀疏问题

除了词表大小本身带来的计算问题之外，还需要考虑**数据稀疏问题**。

词表变大以后，训练数据会被分摊到更多 token 上，因此很多 token 出现的次数会很少，得到的训练机会也不足。

例如，假设有一个罕见词：

```text
深度神经网络压缩技术
```

### 3.1 大词表

在大词表中，它可能被整体作为一个 token：

```text
[深度神经网络压缩技术]
```

但是这个 token 在整个训练语料中可能只出现过 3 次，因此模型很难将它学习好。

### 3.2 小词表

在较小的词表中，它可能被拆分为：

```text
[深度] [神经] [网络] [压缩] [技术]
```

虽然完整短语只出现过 3 次，但是这些组成部分可能分别出现过很多次：

```text
“深度”出现 20000 次
“神经”出现 15000 次
“网络”出现 100000 次
“压缩”出现 12000 次
“技术”出现 80000 次
```

因此，这些较小的 token 可以在不同句子和不同上下文中被反复训练，从而得到更加充分的学习。

---

## 4. Unicode 字符分词器的问题

当然，即使词表非常大，本身也仍然会存在一些生僻字符的稀疏问题。

例如，Unicode 字符分词器可以保证每个 Unicode 字符都有对应的 token，不会出现无法表示某个字符的问题。

但是，它只是把数据稀疏问题从：

```text
罕见长词
```

变成了：

```text
罕见字符
```

也就是说，Unicode 字符分词器可以避免未知字符的问题，但不能完全消除数据稀疏问题。

某些生僻字符在训练语料中仍然可能只出现过很少次数，因此对应 token 的 embedding 和相关参数仍然可能得不到充分训练。

---

## 5. Byte Tokenizer

另一种非常简单的分词方法是 **Byte Tokenizer（字节分词器）**。

它的基本思路是：

1. 先使用 UTF-8 将字符串编码成字节序列；
2. 将每一个字节作为一个 token；
3. 每个 token 的编号就是对应字节的数值。

例如：

```text
Hello, 🌍! 你好!
```

使用 UTF-8 编码后，可以得到类似下面的字节序列：

```text
72 101 108 108 111 44 32
240 159 140 141
33 32
228 189 160
229 165 189
33
```

其中：

```text
H   -> 72
e   -> 101
🌍  -> 240 159 140 141
你  -> 228 189 160
好  -> 229 165 189
```

Byte Tokenizer 将每个字节都看成一个独立 token，因此：

```text
🌍
```

会被编码成：

```text
[240] [159] [140] [141]
```

而不是一个 token。

### 5.1 Byte Tokenizer 的词表大小

一个 byte 可以表示的数值范围是：

```text
0 ～ 255
```

因此，Byte Tokenizer 的词表大小固定为：

$$
V = 256
$$

也就是：

```text
vocabulary_size = 256
```

Byte Tokenizer 不需要提前收集所有可能出现的汉字、单词、符号和 emoji，只需要保存 256 种字节即可。

---

## 6. Bit、Byte 与文件存储

### 6.1 Bit

bit 是计算机中最基本的二进制单位，一个 bit 只能表示：

```text
0
```

或者：

```text
1
```

### 6.2 Byte

通常情况下：

$$
1\ \text{Byte} = 8\ \text{bit}
$$

因此，一个 byte 可以表示：

$$
2^8 = 256
$$

种不同状态。

它们的二进制范围是：

```text
00000000 ～ 11111111
```

对应的十进制范围是：

```text
0 ～ 255
```

所以 Byte Tokenizer 才只需要 256 个基础 token。

### 6.3 Byte 与文件大小

Byte 确实是计算机存储空间中常用的单位。

例如：

```text
1 KB = 1024 Byte
1 MB = 1024 KB
1 GB = 1024 MB
```

无论是文本文件、图片、音频、视频还是程序，最终在计算机中都可以看成一串 byte。

例如，一个 UTF-8 文本文件中：

```text
A
```

通常占用 1 Byte，而：

```text
你
```

通常占用 3 Byte。

需要注意的是，文件的实际数据大小和磁盘占用空间不一定完全相同。

例如，一个只有 6 Byte 的文件，由于文件系统通常按照固定大小的磁盘块进行存储，它在磁盘上实际占用的空间可能大于 6 Byte。

另外，Byte Tokenizer 中的“一个 byte 对应一个 token”，表示的是一个 token 代表一个原始字节。

它并不意味着这个 token 在模型显存中一定只占 1 Byte。

实际训练时，token ID 可能使用：

```text
int32
```

或者：

```text
int64
```

进行保存，因此一个 token ID 在内存中可能占用 4 Byte 或 8 Byte。

---

## 7. Unicode 与 UTF-8

需要区分下面三个概念：

```text
字符
Unicode 编号
UTF-8 字节序列
```

例如，字符：

```text
🌍
```

对应的 Unicode 编号是：

```text
U+1F30D
```

Unicode 负责规定：

> 每一个字符对应什么编号。

但是计算机最终需要将这些编号转换成 byte 才能保存。

UTF-8 就是一种将 Unicode 编号转换成字节序列的编码方法。

因此，完整过程是：

```text
字符
↓
Unicode 编号
↓
UTF-8 编码
↓
字节序列
```

例如：

```text
H   -> U+0048  -> 72
你  -> U+4F60  -> 228 189 160
🌍  -> U+1F30D -> 240 159 140 141
```

所以：

* Unicode 规定字符对应的编号；
* UTF-8 规定这个编号如何变成 byte；
* Byte Tokenizer 再将每个 byte 作为一个 token。

---

## 8. UTF-8 如何判断字符边界

一个重要问题是：

```text
🌍 -> 240 159 140 141
```

反向解码时，计算机怎么知道这四个 byte 表示一个字符，而不是四个字符？

答案是：UTF-8 在每个字节的二进制开头中保存了格式信息。

UTF-8 的基本规则如下：

| 字节开头       | 含义          |
| ---------- | ----------- |
| `0xxxxxxx` | 单字节字符       |
| `110xxxxx` | 两字节字符的第一个字节 |
| `1110xxxx` | 三字节字符的第一个字节 |
| `11110xxx` | 四字节字符的第一个字节 |
| `10xxxxxx` | 前一个字符的后续字节  |

### 8.1 英文字符

例如：

```text
H -> 72
```

72 的二进制表示为：

```text
01001000
```

它以：

```text
0
```

开头，符合：

```text
0xxxxxxx
```

因此 UTF-8 解码器知道，这是一个完整的单字节字符。

### 8.2 中文字符

例如：

```text
你 -> 228 189 160
```

转换成二进制为：

```text
228 -> 11100100
189 -> 10111101
160 -> 10100000
```

它的整体格式是：

```text
1110xxxx 10xxxxxx 10xxxxxx
```

第一个字节以：

```text
1110
```

开头，表示这是一个三字节字符。

因此，UTF-8 解码器会读取当前字节以及后面的两个字节，将它们共同恢复成字符：

```text
你
```

### 8.3 Emoji 字符

例如：

```text
🌍 -> 240 159 140 141
```

转换成二进制为：

```text
240 -> 11110000
159 -> 10011111
140 -> 10001100
141 -> 10001101
```

它的格式是：

```text
11110xxx 10xxxxxx 10xxxxxx 10xxxxxx
```

第一个字节以：

```text
11110
```

开头，表示这是一个四字节字符。

后面三个字节都以：

```text
10
```

开头，说明它们是前面字符的后续字节，而不是三个新字符。

因此，UTF-8 解码器会将：

```text
240 159 140 141
```

共同恢复成：

```text
🌍
```

---

## 9. Byte Tokenizer 本身是否知道字符边界

严格来说，Byte Tokenizer 本身并不知道字符边界。

对于 Byte Tokenizer 来说：

```text
🌍
```

只是四个独立的 token：

```text
[240] [159] [140] [141]
```

Byte Tokenizer 只负责完成：

```text
字符串
↓
UTF-8 字节
↓
token ID
```

在反向解码时，它先完成：

```text
token ID
↓
UTF-8 字节
```

然后再由 UTF-8 解码器根据字节的二进制格式恢复字符。

完整过程是：

```text
🌍
↓ Unicode
U+1F30D
↓ UTF-8 编码
240 159 140 141
↓ Byte Tokenizer
[240] [159] [140] [141]
```

反向过程是：

```text
[240] [159] [140] [141]
↓ Byte Tokenizer
240 159 140 141
↓ UTF-8 解码
U+1F30D
↓
🌍
```

因此，不是模型根据语义猜测这四个 token 应该组成一个 emoji，而是 UTF-8 的编码规则明确规定了它们应该如何组合。

---

## 10. Byte Tokenizer 解决的问题

Byte Tokenizer 主要解决了以下问题。

### 10.1 词表非常小

它的词表固定只有：

$$
256
$$

个 token。

不需要为每个汉字、单词、特殊符号或者 emoji 单独建立词表项。

### 10.2 不会出现未知字符

任何字符串最终都可以被转换成 byte。

因此，即使出现从未见过的：

```text
生僻汉字
新单词
特殊符号
emoji
代码
网址
```

Byte Tokenizer 仍然可以将其编码。

它不会像传统单词分词器一样产生：

```text
<UNK>
```

也就是 unknown token。

### 10.3 编码过程可以完全还原

只要字节序列合法，就可以通过 UTF-8 解码恢复原始字符串。

因此，Byte Tokenizer 通常具有很好的可逆性：

```text
decode(encode(text)) = text
```

---

## 11. Byte Tokenizer 的压缩比问题

Byte Tokenizer 最大的问题是压缩比很差。

因为它规定：

```text
1 Byte = 1 Token
```

所以按照前面的压缩比定义：

$$
\text{Compression Ratio}
========================

\frac{\text{Number of Bytes}}
{\text{Number of Tokens}}
$$

Byte Tokenizer 的压缩比通常为：

$$
\text{Compression Ratio} = 1
$$

这意味着它几乎没有对原始字节序列进行压缩。

### 11.1 英文

英文 ASCII 字符通常一个字符占 1 Byte。

例如：

```text
Hello
```

大约需要：

```text
H e l l o
```

共 5 个 byte，也就是 5 个 token。

### 11.2 中文

一个常见汉字在 UTF-8 中通常占用 3 Byte。

例如：

```text
你好
```

会被编码成：

```text
你 -> 228 189 160
好 -> 229 165 189
```

因此两个汉字需要 6 个 Byte Token：

```text
[228] [189] [160] [229] [165] [189]
```

也就是说：

```text
2 个汉字 -> 6 个 token
```

### 11.3 Emoji

很多 emoji 在 UTF-8 中占用 4 Byte。

例如：

```text
🌍
```

会变成：

```text
[240] [159] [140] [141]
```

因此一个 emoji 就需要 4 个 token。

某些看起来只有一个图形的 emoji，实际上可能由多个 Unicode 字符组合而成，例如：

```text
家庭 emoji
带肤色的 emoji
国旗 emoji
职业 emoji
```

它们可能需要更多 byte，因此也会产生更多 token。

---

## 12. 序列过长带来的问题

假设一段中文有 1000 个汉字。

如果使用较好的子词分词器，可能只需要大约：

```text
1000 ～ 1500 个 token
```

但是如果使用纯 Byte Tokenizer，中文字符通常每个需要 3 Byte，因此可能需要接近：

```text
3000 个 token
```

这会带来以下问题：

* 能放入上下文窗口的实际文本减少；
* 模型训练速度变慢；
* 推理速度变慢；
* 显存占用增加；
* 注意力计算量增加；
* 模型需要自己学习如何将多个 byte 组合成字符和词语。

标准 Transformer 的注意力计算复杂度大约为：

$$
O(n^2)
$$

假设序列长度从：

$$
n
$$

增加到：

$$
3n
$$

那么注意力计算量会从：

$$
n^2
$$

增加到：

$$
(3n)^2 = 9n^2
$$

所以，序列长度增加 3 倍时，注意力部分的计算量理论上可能增加到原来的 9 倍。

---

## 13. Byte Tokenizer 与 Unicode 字符分词器的区别

Byte Tokenizer 和 Unicode 字符分词器并不是同一种方法。

### 13.1 Unicode 字符分词器

Unicode 字符分词器将每个 Unicode 字符作为一个 token。

例如：

```text
你好🌍
```

可能被分成：

```text
[你] [好] [🌍]
```

共 3 个 token。

它的优点是字符序列相对较短，但是需要一个很大的字符词表，并且生僻字符仍然存在数据稀疏问题。

### 13.2 Byte Tokenizer

Byte Tokenizer 将每个 UTF-8 byte 作为一个 token。

同样的字符串：

```text
你好🌍
```

会被分成：

```text
[228] [189] [160]
[229] [165] [189]
[240] [159] [140] [141]
```

共 10 个 token。

它的词表只有 256，但是序列明显更长。

两者的区别可以总结为：

| 方法             |    词表大小 | 未知字符   | 序列长度 | 主要问题       |
| -------------- | ------: | ------ | ---- | ---------- |
| Unicode 字符分词器  |      很大 | 通常可以避免 | 相对较短 | 生僻字符稀疏、词表大 |
| Byte Tokenizer | 固定为 256 | 不会出现   | 很长   | 压缩比差、计算成本高 |

---

## 14. 从 Byte Tokenizer 到 BPE

纯 Byte Tokenizer 的优点是：

```text
词表小
没有未知字符
可以表示任意字符串
```

但是它的缺点是：

```text
序列太长
压缩比太低
```

因此，可以在 byte 的基础上进一步合并经常共同出现的字节序列。

例如，最初：

```text
人 | 工 | 智 | 能
```

可能分别由多个 byte token 表示。

如果训练语料中：

```text
人工智能
```

经常出现，就可以逐步将相关 byte 序列合并成更大的 token。

类似地，英文中的：

```text
t | h | e
```

也可以被合并成：

```text
the
```

这就是 Byte-level BPE 的基本思想：

1. 使用 byte 作为最基础的单位；
2. 保证任意字符串都可以被表示；
3. 将高频出现的 byte 序列合并成更大的 token；
4. 提高压缩比，减少序列长度。

因此，Byte-level BPE 在两个极端之间进行了折中：

```text
纯 Byte Tokenizer：
词表很小，但序列很长

纯单词 Tokenizer：
序列较短，但词表很大，并且容易出现未知词

Byte-level BPE：
保留 byte 的通用性，同时通过合并提高压缩比
```

它希望同时实现：

* 不出现未知字符；
* 词表大小可控；
* 高频文本使用较少 token；
* 序列长度不会像纯 Byte Tokenizer 那么长。

# Byte Pair Encoding

## 1. 基本思路

Byte Pair Encoding 的基本思路是：

```text
在原始文本上训练 tokenizer，
构建一个针对当前数据集的词表。
```

也就是：

```text
train tokenizer on raw text
to construct a vocabulary tailored to the data
```

对于罕见的序列，可以将其拆分成多个较小的 token。

对于经常出现的序列，则可以将其中出现频率最高的相邻 token 合并，创建一个新的 token。

例如，最初的基础词表可能包含 256 个 byte token。

假设当前出现频率最高的相邻 token 是：

```text
t | h
```

那么可以将它们合并成一个新的 token：

```text
th
```

这个新 token 可以被加入词表中，例如成为：

```text
token 256
```

之后继续统计新的 token 序列中，出现频率最高的相邻 token，并重复进行合并。

## 2. BPE 的主要特点

BPE 可以根据训练数据中的实际频率构造词表：

* 高频出现的相邻 token 会被逐步合并；
* 罕见序列仍然可以拆分成多个较小 token；
* 不需要将每个完整单词都加入词表；
* 可以在词表大小和序列长度之间进行折中。

# Using the Tokenizer
